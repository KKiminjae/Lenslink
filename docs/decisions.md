# Technical Decisions

## SearchPlatform 인터페이스를 만든 이유

플랫폼마다 검색 방식, 응답 구조, API가 모두 다르다.

공통 인터페이스를 사용하여
플랫폼이 추가되어도 기존 코드를 수정하지 않는
확장 가능한 구조를 선택하였다.

---

## Musinsa를 보류한 이유

공식 API는 제공되지 않았으며,
내부 API는 브라우저 환경 의존성이 높았다.

유지보수 비용과 안정성을 고려하여
우선순위를 낮추었다.

---

## KREAM을 조사한 이유

HTML에 SSR 데이터(__NUXT_DATA__)가 포함되어 있었다.

공식 API가 없어도
검색 기능 구현 가능성이 있다고 판단하였다.

---

## 공식 API 우선 전략

역공학 기반 구현보다

공식 API를 우선 연동하여

안정성과 유지보수성을 확보하기로 결정하였다.

---

## NAVER Shopping API를 채택한 이유

NAVER Shopping Search API는
공식적으로 지원되는 REST API이며,

WebClient를 이용한 연동이 쉽고,

현재 프로젝트의 SearchPlatform 구조와도
자연스럽게 통합할 수 있었다.

따라서 상품 검색 기능은
NAVER Shopping API를 우선 적용하기로 결정하였다.

---

## SearchPlatform 예외 처리 정책

### 결정

외부 API 호출 실패는
서비스 전체 실패로 처리하지 않는다.

### 이유

SearchPlatform은
플랫폼별 독립성을 위해 만든 구조이다.

따라서

- Naver 실패
- Kream 검색
- Musinsa 검색

은 서로 영향을 주지 않아야 한다.

외부 API 예외는
로그를 남기고 빈 리스트를 반환한다.

NullPointerException은
프로그래밍 버그이므로
catch하지 않고 수정한다.

---

## SearchResponse 도입

### 문제

기존 API는 List<ProductResponse>만 반환하였다.

이 경우

- AI 분석 결과
- 상품 검색 결과

를 동시에 전달할 수 없었다.

또한 프론트엔드가 새상품과 중고상품을 직접 분류해야 했다.

---

### 결정

SearchResponse를 도입하여

- analysis
- newProducts
- usedProducts

를 함께 반환하도록 변경하였다.

새상품과 중고상품 분리는 SearchService에서 수행한다.

---

### 이유

- AI 분석 결과와 검색 결과를 하나의 응답으로 제공할 수 있다.
- 프론트엔드가 별도의 분류 로직 없이 바로 화면을 구성할 수 있다.
- UI 구조(🛍 새상품 / ♻️ 중고)와 API 구조를 일치시킬 수 있다.
- 앞으로 새로운 플랫폼을 추가해도 응답 구조를 유지할 수 있다.

---

## platform과 mall을 분리한 이유

기존에는 mall 필드 하나만 사용하였다.

하지만 네이버 쇼핑 API의 mallName은 실제 판매처를 의미하며,
검색이 수행된 플랫폼과는 다른 개념이다.

예를 들어

- platform : Naver Shopping
- mall : 트렌비

처럼 서로 다른 정보를 표현해야 한다.

따라서 검색 플랫폼과 판매처를 명확히 구분하기 위해
platform 필드를 추가하였다.

이 구조는 추후 무신사, KREAM, 번개장터 등 여러 검색 플랫폼을 추가할 때도 그대로 사용할 수 있다.

---

## 검색 후보 생성과 검색 결과 평가를 분리한 이유

기존에는 NaverShoppingService가 다음 책임을 모두 가지고 있었다.
- 검색 후보 생성
- 네이버 쇼핑 API 호출
- 검색 결과 평가
- 검색 재시도

서비스의 책임이 많아질수록 테스트와 유지보수가 어려워진다.

따라서 검색 후보 생성과 평가를 각각 독립적인 클래스로 분리하였다.

그 결과 NaverShoppingService는 검색 흐름만 제어하도록 변경하였다.

### 이유
- 단일 책임 원칙을 적용하기 위ㅜ해
- 검색 후보 생성과 결과를 각각 독립적으로 테스트 하기 위해
- 향후 다른 쇼핑 플랫폼에서도 동일한 로직을 재사용하기 위해

---

## 검색 후보 우선순위

검색 성공률을 높이기 위해 검색 범위를 좁은 것에서 넓은 것으로 확장하도록 설계하였다.

``` text
1. 브랜드 + 상품명
2. 상품명
3. Similar Products (confidence 높은 순)
4. 브랜드
```
브랜드 검색은 범위가 가장 넓기 때문에 마지막으로.

---

## SearchNormalizer를 도입한 이유

플랫폼마다 브랜드명과 상품명이 서로 다른 형식으로 저장되어 있다.

예를 들어

```text
Nike®
nike
 NIKE
```

는 모두 동일한 브랜드지만 문자열 비교만으로는 서로 다르게 인식된다.

이를 해결하기 위해 SearchNormalizer를 도입하였다.

SearchNormalizer는

- 앞뒤 공백 제거
- 소문자 변환
- 특수문자 제거
- 공백 정규화

를 공통으로 수행한다.

모든 검색 후보 생성과 검색 결과 평가는 동일한 정규화 규칙을 사용하도록 설계하였다.

### 장점

- 문자열 비교 규칙을 한 곳에서 관리
- 중복 코드 제거
- 검색 성공률 향상
- 향후 브랜드 별칭(예: 나이키 → nike) 확장 가능

---

## 검색 이력을 분석 직후 저장한 이유

### 선택한 설계

OpenAI 이미지 분석이 성공하면 검색 이력을 즉시 DB에 저장한다.

### 선택 이유

- 모든 성공한 이미지 분석 결과를 기록할 수 있다.
- 향후 검색 기록 조회 기능을 쉽게 추가할 수 있다.
- 검색 데이터 분석 및 추천 기능의 기반이 된다.
- 검색 플랫폼 로직과 검색 이력 저장을 분리할 수 있다.

### 고려했던 대안

#### 1. 상품 검색 이후 저장

장점

- 실제 검색이 성공한 경우만 저장된다.

단점

- 검색 과정에서 실패하면 분석 결과도 함께 사라진다.

#### 2. 비동기(Event) 저장

장점

- 응답 속도가 조금 더 빨라질 수 있다.
- 확장성이 좋다.

단점

- 현재 MVP 단계에서는 구조가 불필요하게 복잡해진다.

### 최종 결정

현재는 단순하고 유지보수가 쉬운 동기(JPA) 저장 방식을 사용하고,
트래픽이 증가하면 이벤트 기반 비동기 저장으로 확장한다.

---

## SearchHistoryService를 분리한 이유

최근 검색 조회 기능은 SearchService에 추가하지 않고 별도의 SearchHistoryService로 분리하였다.

### 이유

- SearchService는 이미지 분석 및 상품 검색을 담당한다.
- SearchHistoryService는 검색 기록 조회만 담당한다.
- 서비스별 책임을 명확하게 분리하여 단일 책임 원칙(SRP)을 유지한다.
- 향후 검색 기록 관련 기능(삭제, 페이징, 검색 등)이 추가되어도 SearchService의 복잡도가 증가하지 않는다.

---

## Entity 대신 DTO를 반환한 이유

API 응답으로 SearchHistory 엔티티를 그대로 반환하지 않고 SearchHistoryResponse DTO를 반환하도록 설계하였다.

### 이유

- 데이터베이스 구조를 외부에 노출하지 않기 위해
- 프론트엔드에서 필요한 데이터만 전달하기 위해
- Entity 변경이 API 변경으로 이어지는 것을 방지하기 위해
- API와 데이터베이스를 독립적으로 관리하기 위해

---

## 최근 검색을 Top3로 조회한 이유

최근 검색 API는 최신 검색 기록 3개만 반환하도록 구현하였다.

### 이유

- 현재 Flutter 와이어프레임과 동일한 개수를 제공하기 위해
- 불필요한 데이터 조회 및 응답 크기를 줄이기 위해
- MVP 단계에서는 단순한 구조를 유지하기 위해
- 향후 더보기 기능이나 페이징이 필요할 경우 쉽게 확장할 수 있도록 고려하였다.

---
## SearchResultEvaluator 비교 방식 개선

### 문제

기존에는

actual.contains(expected)

방식으로 상품명을 비교하였다.

그러나 쇼핑몰마다

- 색상
- 모델 코드
- 브랜드명
- 상품 설명

등이 추가되어 동일 상품임에도 문자열 전체가 일치하지 않는 경우가 많았다.

예시

기대

DRKSHDW Low-Top Distressed Canvas Sneaker

실제

릭오웬스 DRKSHDW 스니커즈 블랙밀크 DU01F4800

---

### 선택

상품명을 공백 기준으로 분리하여 토큰 단위로 비교하도록 변경하였다.

공통 토큰이 일정 개수 이상 존재하면 동일 상품으로 판단한다.

---

### 선택 이유

- 쇼핑몰마다 상품명 표현이 다르다.
- 색상 및 모델 코드가 추가되는 경우가 많다.
- 문자열 전체 비교보다 실제 검색 환경에 적합하다.

---

## 검색 기록에 imageUrl을 저장한 이유

### 문제

기존에는 검색 기록에 searchKeyword를 저장하고 있었다.

하지만 최근 검색 화면에서는 사용자가 입력했던 검색어보다 상품 이미지가 더 중요한 정보이다.

### 선택

searhKeyword를 제거하고 imageUrl을 저장하도록 변경하였다.

### 선택 이유

- 최근 검색 화면에서 바로 상품을 식별할 수 있다.
- 프론트엔드에서 별도의 이미지 조회 API가 필요 없다.
- 검색 당시의 대표 이미지를 그대로 사용할 수 있다.

### Trade-off

장점
* 조회 성능이 단순하다.
* UI 구현이 쉬워진다.

단점 
* 이미지 URL이 변경되면 이전 기록에는 반영되지 않는다.
* 대표 이미지를 첫 번째 검색 결과로 결정한다는 가정이 있다.

현재 MVP에서는 대표 이미지를 첫 번째 검색 결과로 사용하는 것이 충분하다고 판단하였다.

## Pageable을 사용한 이유

검색 기록은 시간이 지날수록 데이터가 계속 증가한다.

모든 데이터를 한 번에 조회하는 방식은

- 메모리 사용 증가
- 응답 시간 증가
- 네트워크 낭비

문제가 발생할 수 있다.

따라서 Spring Data JPA의 Pageable을 사용하였다.

---

## Page를 반환한 이유

List는 데이터만 반환한다.

Page는

- content
- totalElements
- totalPages
- hasNext

등의 정보를 함께 제공한다.

프론트는 이를 이용하여

- 페이지 이동
- 무한 스크롤
- 다음 데이터 요청

등을 쉽게 구현할 수 있다.

## 최근 검색과 검색 기록 API를 분리한 이유

최근 검색은 Home 화면에서 빠르게 조회해야 한다.

검색 기록은 전체 목록을 조회한다.

용도가 다르기 때문에 API를 분리하였다.

GET /history/recent

↓

Top3 조회

GET /history

↓

Pageable 조회

## Docker Volume을 선택한 이유

초기에는 MySQL 컨테이너 내부에 데이터가 저장되었다.

하지만 컨테이너를 삭제하면 모든 데이터가 함께 삭제되는 문제가 있었다.

이를 해결하기 위해 Docker Named Volume을 적용하였다.

### 장점

- 데이터 영속성 보장
- 컨테이너 재생성 시 데이터 유지
- 개발 및 운영 환경 모두 동일한 방식 사용 가능

---

## Health Check를 적용한 이유

depends_on은 컨테이너의 실행 순서만 보장한다.

하지만 MySQL이 실제 연결 가능한 상태인지까지는 보장하지 않는다.

Health Check를 적용하여 MySQL 준비 완료 이후 Spring Boot가 실행되도록 변경하였다.

### 장점

- DB 초기화 중 연결 실패 방지
- 실행 순서 안정성 향상

---

## Spring Profile을 적용한 이유

개발 환경과 Docker 환경은 DB 주소가 다르다.

Local

localhost:3307

Docker

mysql:3306

기존에는 application.yaml을 직접 수정해야 했다.

Spring Profile을 적용하여 환경별 설정 파일을 분리하고 실행 환경에 따라 자동으로 설정을 선택하도록 변경하였다.

### 장점

- 설정 수정 없이 환경 변경 가능
- 유지보수성 향상
- 운영 환경 확장 용이

# GitHub Actions CI 구축

## Spring Profile을 분리한 이유

환경마다 데이터베이스 주소와 설정이 다르다.

- Local : localhost:3307
- Docker : mysql:3306
- GitHub Actions : localhost:3306

하나의 application.yaml로 관리하면 환경마다 설정을 계속 수정해야 하므로
application-local, application-docker, application-test로 분리하였다.

---

## GitHub Actions에서 MySQL Service를 사용한 이유

실제 프로젝트는 MySQL을 사용한다.

테스트 환경에서도 동일한 데이터베이스를 사용하여
로컬 환경과 최대한 동일한 조건에서 테스트하기 위해
GitHub Actions Service Container를 사용하였다.

H2를 사용하는 것보다 운영 환경과의 차이를 줄일 수 있다.

---

## Test Profile에 Dummy API Key를 사용한 이유

Context Load 테스트에서는 실제 OpenAI API와
Naver Shopping API를 호출하지 않는다.

하지만 Bean 생성 과정에서 @Value가
프로퍼티를 읽기 때문에 값은 반드시 존재해야 한다.

실제 API Key를 저장소에 저장하지 않기 위해
Dummy 값을 사용하였다.

---

## GHCR 기반 배포를 선택한 이유

## 기존 방식

EC2에서 직접 Docker 이미지를 빌드하였다.

### 장점

- 설정이 단순하다.

### 단점

- EC2 리소스를 사용하여 빌드한다.
- 빌드 시간이 길어진다.
- CI에서 검증한 결과와 다른 환경에서 다시 빌드된다.

---

## 변경

GitHub Actions에서 이미지를 빌드한 후 GHCR에 저장하고, EC2에서는 이미지만 Pull하도록 변경하였다.

### 장점

- 빌드는 한 번만 수행된다.
- CI에서 검증한 이미지가 그대로 운영 환경에 배포된다.
- EC2는 실행만 담당하여 배포 시간이 단축된다.
- CI와 CD의 역할이 명확하게 분리된다.

### Trade-off

- GHCR 관리가 필요하다.
- Docker Registry 인증을 추가해야 한다.

---

## Nginx Reverse Proxy를 도입한 이유

## 배경

기존에는 사용자가 Spring Boot(8080)에 직접 접근하는 구조였다.

운영 환경에서는 일반적으로 웹 서버(Nginx)를 통해 요청을 처리한 후
애플리케이션 서버(Spring Boot)로 전달하는 구조를 사용한다.

---

## 선택한 설계

Browser

↓

Nginx

↓

Spring Boot

---

## 선택 이유

### 1. 운영 환경과 동일한 구조

실제 서비스에서 가장 많이 사용하는 Reverse Proxy 구조를 적용하였다.

---

### 2. Spring Boot 외부 노출 제거

Spring Boot는 expose를 사용하여 Docker 내부에서만 접근 가능하도록 변경하였다.

외부에서는 Nginx만 접근 가능하다.

---

### 3. 향후 확장성 확보

Nginx를 사용하면 다음 기능을 쉽게 추가할 수 있다.

- HTTPS
- SSL 인증서
- 정적 파일 제공
- Gzip 압축
- Rate Limiting
- Load Balancing

---

## Trade-off

Nginx 컨테이너가 하나 추가되므로 구성은 조금 복잡해진다.

하지만 운영 환경과 동일한 구조를 만들 수 있고,
보안성과 확장성이 크게 향상된다.

---

## HTTPS 처리를 Spring Boot가 아닌 Nginx에서 수행

### 결정

외부 HTTPS 연결은 Nginx에서 종료하고,
Nginx와 Spring Boot 사이에서는 Docker 내부 HTTP 통신을 사용한다.

```text
Client
  │ HTTPS
  ▼
Nginx
  │ HTTP
  ▼
Spring Boot
```

### 선택 이유

- 인증서 관리 지점을 Nginx 한 곳으로 집중할 수 있다.
- Spring Boot 애플리케이션과 TLS 설정의 책임을 분리할 수 있다.
- 인증서 갱신 시 Spring Boot 애플리케이션을 재배포할 필요가 없다.
- HTTP에서 HTTPS로의 리다이렉트를 Nginx에서 처리할 수 있다.
- 향후 여러 애플리케이션이나 서버 인스턴스로 확장하기 쉽다.
- 로드밸런싱, 압축, 캐싱 등의 기능을 Nginx에서 추가할 수 있다.

### 대안

Spring Boot의 내장 Tomcat에 인증서와 keystore를 설정하여
애플리케이션이 HTTPS를 직접 처리할 수도 있다.

하지만 이 방식은 인증서 관리가 애플리케이션 설정과 결합된다.

서비스가 늘어날수록 인증서 배포 및 갱신 지점도 증가하므로,
현재 구조에서는 Nginx TLS Termination 방식이 운영 복잡도를 낮춘다고 판단했다.

## Certbot을 Docker 컨테이너로 실행

### 결정

EC2 운영체제에 Certbot을 직접 설치하지 않고
`certbot/certbot` Docker 이미지를 사용한다.

### 선택 이유

- 현재 운영 환경이 Docker Compose 기반이다.
- EC2 운영체제에 별도 패키지를 설치하지 않아도 된다.
- Certbot 실행 환경을 Compose 설정으로 재현할 수 있다.
- Nginx와 Docker volume을 통해 검증 파일과 인증서를 공유하기 쉽다.
- 인증서 발급과 갱신 작업 후 일회성 컨테이너를 삭제할 수 있다.

### 트레이드오프

Certbot 컨테이너는 상시 실행되지 않는다.

따라서 인증서 자동 갱신을 위해 cron과 같은
별도의 스케줄링 방식이 필요하다.

---

## 인증서와 검증 파일을 Docker named volume에 저장

### 결정

다음 두 named volume을 사용한다.

```text
certbot-webroot
letsencrypt
```

### 선택 이유

- 컨테이너 재생성 후에도 인증서가 유지된다.
- Certbot과 Nginx가 동일한 파일을 공유할 수 있다.
- 개인키가 프로젝트 디렉터리와 Git 저장소에 포함되지 않는다.
- Nginx에는 읽기 전용 권한만 부여할 수 있다.

### 권한 설계

```text
Certbot
→ 검증 파일과 인증서 쓰기 가능

Nginx
→ 검증 파일과 인증서 읽기 전용
```

최소 권한 원칙에 따라 Nginx가 사용하는 volume에는
`:ro` 옵션을 적용했다.

## 운영 안정성 설정

### Application 메모리 제한을 384MiB로 둔 이유

현재 EC2는 약 1GB 메모리 환경이며, Spring Boot와 MySQL이 같은 서버에서 실행된다.

Application 컨테이너에 384MiB 제한을 적용해 앱이 호스트 메모리를 과도하게 점유하지 못하도록 했다.

가벼운 조회 API 반복 호출에서는 큰 문제 없이 동작했지만, 실제 이미지 분석 요청 후 메모리 사용량이 약 312MiB까지 증가했다. 따라서 현재 설정은 단일 요청에는 동작하지만 동시 이미지 요청에는 여유가 부족할 수 있다.

대안은 다음과 같다.

* Application 메모리 제한을 512MiB 이상으로 증가
* EC2 메모리를 2GB 이상으로 확장
* 이미지 크기 제한 및 리사이징 적용
* 이미지 분석 동시 실행 수 제한
* 장기적으로 이미지 분석 작업을 별도 Worker로 분리

현재 서버에서 앱 제한만 올리면 MySQL과 운영체제 메모리를 압박할 수 있으므로, 단순 증설보다 요청당 메모리 최적화와 서버 사양 확장을 함께 검토한다.

### Docker 로그 회전 정책을 적용한 이유

Docker 기본 로그는 별도 제한이 없으면 계속 증가해 EC2 디스크를 고갈시킬 수 있다.

이를 방지하기 위해 다음 정책을 적용했다.

```yaml
logging:
  driver: json-file
  options:
    max-size: 10m
    max-file: "3"
```

컨테이너당 로그 파일을 약 30MB 범위로 제한해 디스크 고갈 위험을 줄인다.

대신 로그 발생량이 많으면 오래된 로그가 빠르게 삭제될 수 있다. 장기 보관이 필요해지면 중앙 로그 수집 시스템을 별도로 도입해야 한다.

### 인증서 갱신을 Cron으로 자동화한 이유

Let's Encrypt 인증서는 유효기간이 제한돼 있어 갱신 작업이 실패하면 HTTPS 서비스가 중단될 수 있다.

매일 오전 3시에 Certbot 갱신을 시도하고, 명령 성공 후 Nginx가 인증서를 다시 읽도록 reload하는 구조를 사용한다.

`certbot renew --dry-run`으로 현재 설정에서 인증서 갱신 절차가 정상적으로 수행 가능한지 확인했다.
